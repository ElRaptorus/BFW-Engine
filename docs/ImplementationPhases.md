Generates `ProcessModel` (with both a nested `flowNodes` tree and a flat, every-scope `allFlowNodes` index carrying `parentSubProcessId`, per D-2 = C), the `FlowNode` interface, one concrete node type per `FlowNodeData.*` struct (21, struct-aligned per D-1 = A — event *kind* is a separate `EventDefinition` union, not folded into the enum), and the `EventDefinition` union (11 members). `ProcessVersion.processModel` + `FlowNodeInstance.flowNode`/`FlowNodeInstance.processVersion` resolvers (`model_resolvers.ex`) read `EvilEngine.BPMN.ModelCache`; a `Dataloader.KV` source (`dataloader/model_cache_source.ex`) batches all `flowNode` resolutions sharing a `process_version_id` into one `ModelCache.fetch/1` call per request; `ProcessVersion.bpmnXml` retained. (b) `evil_engine_sdk` re-export — `EvilEngine.SDK.BPMN` (`apps/engine_sdk/lib/evil_engine/sdk/bpmn.ex`) delegates `parse/1`, `fetch_definitions/1`, `get_definitions/1`, `fetch_subprocess_model/2`, `find_message_start_events/1`, `find_signal_start_events/1` to `EvilEngine.BPMN.{Parser, ModelCache}`, so in-engine plugins and out-of-tree Elixir tooling can parse + consume the AST with the engine's semantics. (c) **Superseded by decision D-5 = B+** (see `.cursor/plans/process_model_graphql_exposure_205a61a4.plan.md` §5): a generated `moddle/evil.json` was rejected because the Engine's parser (`sax_handler.ex`) has no `allowed_in`/type-hierarchy concept to generate it from — inventing that data would move an authoring-time modelling concern into the wrong repository. Instead the Engine ships a smaller, honestly-generatable **extension vocabulary manifest**: `mix evil.gen.extension_manifest` (`apps/core_bpmn/lib/mix/tasks/evil.gen.extension_manifest.ex`) emits `extension-manifest.json` from `EvilEngine.BPMN.ExtensionManifest`, one entry per `evil:*` element (`element`, `valueKind`, `carrier`, `attributes`, `applicableTo`, `modelField`) plus a top-level `extensible` list (`Properties`/`Property`). Shipped as a typed export in `@elraptorus/daemonengine_sdk` (`packages/js/sdk/src/generated/extension-manifest.ts`), not a client-side npm package named `@evil/engine-client` (that name was stale documentation — the real packages are `@elraptorus/daemonengine_sdk` and `@elraptorus/daemonengine_client`, D-7). The Studio's hand-written `evil-platform.json` moddle descriptor remains Studio-owned; a bidirectional conformance test in the Studio repo checks it against this manifest. Integration/unit tests assert: (i) every `FlowNodeData.*` struct has a matching GraphQL concrete type, every `EventDefinition.*` struct has a matching union member, every FieldTable `exposed` atom exists on the mapped Absinthe type, and every `Model.*` struct module is registered (`EvilEngineWeb.Graphql.ModelGraphIntrospectionTest`); (ii) `allFlowNodes` matches a direct `Model.Process` tree walk across every parseable fixture BPMN (`ModelResolversTest`) and `FlowNodeInstance.flowNode` reaches inner-scope nodes with `parentSubProcessId` set (`graphql_model_graph_wp7_test.exs`); (iii) every `evil:*` element in the fixture BPMN corpus has a manifest entry with the value kind the parser actually reads, committed JSON matches `ExtensionManifest.to_map/0`, and `mix evil.gen.extension_manifest --check` is in the `quality` alias and CI (`extension_manifest_test.exs`); (iv) no compiled artifact (`compiled_*`, `precompiled`, `raw_xml`) is reachable through schema introspection (`ModelGraphIntrospectionTest`); (v) Dataloader batching — a debugger-shaped query over a PI with N FNIs issues exactly one `ModelCache.fetch/1` per distinct `process_version_id`, verified via `:telemetry` (`graphql_model_graph_wp7_test.exs`); (vi) an unauthenticated caller cannot reach `processModel` (HTTP 401/403); an actor who cannot read a `FlowNodeInstance` cannot reach `flowNode`/`processVersion` through it (lane isolation). `ProcessVersion` read policy is `actor_present()`, so any authenticated JWT can read `processModel` the same as `bpmnXml`; (vii) a cold `ModelCache` miss still resolves correctly via the DB-backed loader, and the canonical `buildProcessModelSelection(4)`-shaped debugger query passes the depth/complexity limits (`EVIL_GRAPHQL_MAX_DEPTH` default 16).
2. **WebSocket lane-filter (`[Authorization.md](./architecture/authorization.md)` §9)**: Phoenix Channels dispatch-time filtering on `process_instance:<id>`, `process:<key>`, and `user_tasks:pending` topics. Every typed event payload carries the originating FNI's `lane_name` (or `nil`); the connection caches the caller's lane-claim set at join time and silently drops events for FNIs on inaccessible lanes. PI-level events (`ProcessInstanceStateChanged`, `PiFinished`) are delivered iff the PI is visible per the visibility rule (§5.1). Integration tests assert: (i) a subscriber without `lane:Management=true` never receives `FlowNodeInstanceStarted` events for FNIs on the "Management" lane; (ii) events for laneless FNIs are always delivered; (iii) PI-level events are delivered to a subscriber who can see the PI via the starter-match rule even if no active FNI is on an accessible lane.
3. **Sidecar plugin bridge live (§9.2.3 + §9.3 + §14.3)**: `peripheral_plugins.SidecarLoader` scans `EVIL_PLUGINS_SIDECAR_DIR` (default `~/.evil/engine/plugins`, `/etc/evil-engine/plugins` in containers) for `plugin.toml` manifests, validates each manifest against the schema in §9.2.3 (name, binary path, declared categories, gRPC port hint), applies `EVIL_PLUGINS_INCLUDE` / `EVIL_PLUGINS_EXCLUDE` (exclude wins, shared list with the in-BEAM tier), and for each surviving plugin starts the binary under an Erlang `Port` supervised by a one-for-one `Supervisor`. The bridge speaks the plugin gRPC protocol (proto definition vendored in `engine_sdk`); on connection, the engine invokes the gRPC equivalent of `on_load` (passing a stub `engine_facade` that proxies §9.2.5 capabilities back over gRPC) followed by `on_ready` once the engine reports itself ready. Reconnect-with-exponential-backoff up to `EVIL_PLUGINS_SIDECAR_RECONNECT_LIMIT` attempts; after the limit is reached the plugin is **quarantined** — the registry entries it owned are torn down, no further reconnect is attempted on this boot, and an `Event.PluginQuarantined{plugin_name, tier: :sidecar, reason: :reconnect_limit_exceeded, occurred_at}` is published on `EngineEventBus`. Manifest discovery, allow/deny evaluation, `on_load`-RPC, and `on_ready`-RPC failures are quarantined the same way (§9.3). **Multi-language test fixture plugins** live at `test/fixtures/plugins/` (project root, not inside an individual umbrella app) — each subdirectory is a minimal but realistic sidecar plugin with a `plugin.toml` and a runnable binary/script implementing at least one plugin category (e.g. ServiceTaskHandler or EventSink). **Fixture plugins must cover five languages** to prove the language-agnostic claim: Elixir (escript), Python, Ruby, C# (dotnet), and Node.js. Integration tests set `EVIL_PLUGINS_SIDECAR_DIR` to the fixture directory, and cleanup resets the path and disconnects/unloads all sidecar plugins so no cross-test interference occurs. Integration tests cover: (i) a happy-path sidecar custom Service Task plugin written in a non-Elixir language registers, executes, and ships its result back through the registry; (ii) sidecar binary crashes mid-execution → reconnect succeeds → in-flight FNI fails-gracefully via the standard handler-failure path (synchronous `{:error, _}` for non-async returns; the `engine_facade.fail_async_service_task/3` callback for FNIs that returned `{:async, flow_node_instance_id}`); (iii) sidecar binary crashes repeatedly → reconnect-limit reached → `Event.PluginQuarantined` reaches every active sink, no further reconnects on this boot, engine remains healthy; (iv) malformed manifest → plugin quarantined, engine boots, other plugins unaffected; (v) deny-listed sidecar manifest → not even spawned, structured log emitted; (vi) **multi-language proof**: at least one fixture sidecar per language (Elixir, Python, Ruby, C#, Node.js) successfully discovers, handshakes, registers, and executes a Service Task end-to-end; (vii) **sidecar_dir isolation**: integration tests configure the discovery path to `test/fixtures/plugins/`, and cleanup resets the config and unloads/disconnects all sidecar plugins so no state leaks into subsequent tests.
6. **Exit criterion**: both plugin tiers exercised; multi-language sidecar fixtures pass end-to-end; **Process Model graph** (§10.2.2) resolves correctly for every fixture BPMN and Studio-style debugger queries complete in a single round-trip; **WebSocket lane filtering** silently drops events for inaccessible lanes and the visibility filter produces consistent results across GraphQL reads and WS subscriptions; full integration test coverage for all Phase 6 items.


## Phase 7 — Polish, Hardening and Battle Simulation

1. **Load test + benchmark reporting infrastructure**: 10 000 concurrent PIs across linear / parallel / MI / Call Activity chains with varying payload sizes. Identify & eliminate hot paths. Upgrade the Phase 1 `[BENCH]` line output to a structured benchmark reporter that (a) writes per-run JSON reports to `test/load/reports/<timestamp>.json` with PI count, elapsed ms, PIs/sec, BEAM process count, memory usage (`:erlang.memory/0`), and GC stats; (b) computes derived KPIs per workload — resume throughput (PIs/sec), seeding throughput (PIs/sec), p50/p95/p99 latencies for batched operations; (c) optionally compares against a baseline file for regression detection (fail if any KPI regresses by more than 20 %). CI archives reports as build artifacts for trend tracking.
2. Zero-downtime deploy: hot-code-upgrade rehearsal with one process-version bump under active load.
3. Back-pressure controls on message publication. (No external-task queue removed that subsystem; async Service Task plugins own their own queue if they have one, so backpressure for queue-bridge plugins is the plugin's responsibility.)
4. **Housekeeping & retention (§14.6)**: build `peripheral_persistence.RetentionRunner` GenServer with two passes. **Pass A**: per-state policies driven by `EVIL_RETENTION_<STATE>_DAYS` + `EVIL_RETENTION_RUN_INTERVAL` + `EVIL_RETENTION_BATCH_SIZE`. Atomic-per-PI cascade delete across `process_instance_events` / `data_object_writes` / `data_objects` / `flow_node_instances` / `engine_timers` (armed rows owned by PI) / `gateway_pending_arrivals` / `process_instances`, skipping PIs whose children are still `running`. Emit one `Event.RetentionPurged` per deleted PI on `EngineEventBus`. **Pass B**: engine-audit retention driven by `EVIL_RETENTION_ENGINE_AUDIT_DAYS`. Sweeps `messages` / `pending_messages` (`state IN (delivered,expired,cancelled)`) / `signals` / `pending_signals` (`state IN (delivered,expired,cancelled)`) / `escalations` / `pending_escalations` (`state IN (delivered,expired,cancelled)`) / `compensations` / `engine_timers` (`state IN (fired,cancelled)`) via per-table batched DELETE. Emit one `Event.EngineAuditPurged{table,cutoff,row_count}` per table per tick on `EngineEventBus`. Also wire the `EVIL_PENDING_<TYPE>_KEEP_AFTER_TRANSITION=false` paths (one per pending table for messages, signals, and escalations): transition-site in the respective dispatcher + unified `PendingSweeper` issues a `DELETE` instead of a state-update when the flag is off. Ship the GraphQL `purgeProcessInstances` mutation (§10.2.3) guarded by the `:can_purge_audit_data` Ash Policy seeded in Phase 0, the CLI wrapper `evil_engine purge`, and the `mix evil.partitions.ensure` task (boot-time partition pre-create across all nine partitioned tables). Integration tests assert: **Pass A** — (i) atomic cascade under mid-transaction SIGKILL leaves no orphans; (ii) `dryRun: true` touches no rows; (iii) running PIs with still-`running` children are skipped with a structured reason in `PurgeResult`; (iv) `Event.RetentionPurged` reaches every active sink; (v) partitions pre-exist `EVIL_PARTITION_AHEAD_MONTHS` into the future after boot. **Pass B** — (vi) a `messages` row aged past `EVIL_RETENTION_ENGINE_AUDIT_DAYS` is deleted, while `pending_messages.state='pending'` / `pending_signals.state='pending'` / `pending_escalations.state='pending'` rows of the same age are NOT deleted (operational-state exclusion across all three pending tables); (vii) an `engine_timers.state='armed'` row is NOT deleted even when older than cutoff, while `fired`/`cancelled` rows are; (viii) `Event.EngineAuditPurged{table, cutoff, row_count}` is emitted exactly once per non-empty table per tick (eight possible table values now, including the two pending-signal and pending-escalation tables); (ix) `EVIL_PENDING_<TYPE>_KEEP_AFTER_TRANSITION=false` physically deletes rows on state transition across all three pending tables (table count stays flat under delivery load for whichever types have the flag off); (x) engine-audit retention works independently of PI retention — setting only `EVIL_RETENTION_ENGINE_AUDIT_DAYS` (no PI-scoped policy) still boots the runner and executes Pass B; (xi) partition-pruning: an engine-audit sweep with a cutoff 3 months in the past touches only the relevant old partitions (verified via `EXPLAIN ANALYZE`), not the current one.
5. **LZ4 JSONB compression benchmark gate**: under the Phase 6 load test (10 000 concurrent PIs with the standard workload fixture covering linear / parallel / MI / 5-level-deep Call Activity chains and realistic payload sizes up to 64 KiB), measure the median per-operation latency and p95 tail latency for `write_result`, DOA-originated DO writes (DOA-only), `publish_message`, FNI `input_token` reads during resume, and the median GraphQL `processInstances { flowNodeInstances { inputToken outputToken } }` query time — first with `EVIL_JSONB_COMPRESSION=lz4` (default), then with `EVIL_JSONB_COMPRESSION=pglz`. **Gate:** if LZ4 is more than 10 % slower than PGLZ on *any* of these measurements, flip the `EVIL_JSONB_COMPRESSION` default to `pglz` before release, keep LZ4 as an opt-in operator choice, and document the observed overhead in the Phase 6 soak-test report. Baseline expectation from published PG14+ benchmarks on JSONB-heavy workloads: LZ4 is **3-8 % faster** than PGLZ on reads, **2-5 % faster** on writes, with ~10-20 % less storage reduction. If measured numbers diverge materially from that baseline, file an investigation task and re-run before release.
6. **Payload-cap load & chaos**: under the Phase 6 load test, assert (a) `write_result` / DOA-originated DO writes / `publish_*` with payloads exactly at `EVIL_TOKEN_MAX_BYTES` succeed; (b) payloads one byte over return `{:error, :payload_too_large, ...}` from the facade (or from the DOA-commit step for DO writes) with the causing FNI transitioning to `fatal` and no DB state changes; (c) REST `POST /triggers/messages` with an oversized `payload` returns HTTP 413 without inserting a `messages` row; (d) the GraphQL equivalent returns `extensions.code = "PAYLOAD_TOO_LARGE"` with the same `size`/`limit`/`field` shape. Run under a workload that emits a steady 5 % rate of oversize-payload calls for 10 minutes and verify engine memory/queue metrics stay flat — the cap must be enforced before any allocation that scales with payload size.
7. Long-haul soak test: 72-hour run, zero-restart, flat memory graph.
8. Resume-after-crash chaos test: kill engine mid-run, restart, verify every PI resumes correctly — including **payload-cap-specific** assertions: (a) every `state='active'` FNI comes back with its `input_token` intact; (b) `gateway_pending_arrivals` rows correctly drive re-armed parallel-join waits; (c) there are no orphan rows under the retired `active_tokens` name in either the DB or the in-memory PI state (the table no longer exists, the migration must have dropped it cleanly).
9. Documentation pass (README, architecture overview, **plugin authoring guide** covering both tiers — in-BEAM (§9.2.2) for OTP-app plugins bundled in the release with `on_load`/`on_ready` callbacks, sidecar (§9.2.3) for language-agnostic gRPC plugins discovered from `EVIL_PLUGINS_SIDECAR_DIR` with manifest format reference, plus the shared §9.2.5 `engine_facade` capability table and the §9.3 quarantine semantics — deploy guide, **operator retention guide** covering sink selection, PI retention policy sizing, **engine-audit retention** including the `EVIL_PENDING_MESSAGES_KEEP_AFTER_TRANSITION` trade-off and partition-pruning behavior, **operator payload-cap & compression tuning guide** covering `EVIL_TOKEN_MAX_BYTES` / `EVIL_JSONB_COMPRESSION` with the Phase 6 measurement table).
10. **Example plugin cookbook (`examples/` in the engine repo)**: ✅ **Partially delivered early** — 22 examples covering all live plugin capabilities (service task handlers, event sinks, named scripts, lifecycle/API, combined patterns) plus TypeScript SDK and Client examples were shipped ahead of Phase 6. See `[examples/README.md](../examples/README.md)` for the full catalogue. Remaining Phase 6 work: sidecar examples (blocked on Phase 5 sidecar bridge), SSE event sink, CI integration test for each example, and promotion from fixture plugins. Original minimum cookbook contents:
  - `**examples/inbeam/hello-service-task`** (in-BEAM, Elixir) — the smallest possible plugin: an OTP app whose `EvilEngine.Plugin` callback module's `on_load(facade)` registers a single custom Service Task handler that echoes its input as its output. Demonstrates `on_load`, `facade.register_service_task_handler./2`, and the `FlowNodeResult` shape.
    - `**examples/inbeam/lifecycle-aware`** (in-BEAM, Elixir) — uses both lifecycle callbacks: `on_load` registers a no-op handler stub; `on_ready` calls the `processes/0` function through the facade and writes the deployed catalog to a structured log. Demonstrates the `on_load` vs `on_ready` semantic split (§9.2.1) and direct `EvilEngine.Api.*` access from a plugin.
    - `**examples/inbeam/event-sink-stdout**` (in-BEAM, Elixir) — registers an `EventSink` that pretty-prints every `EvilEngine.Types.Event.*` to stdout with severity-based filtering. Demonstrates `facade.register_event_sink.(…)` from `on_load/1` (§9.1, §3.3.2) and the typed-event surface re-exported from `evil_engine_sdk`.
    - `**examples/inbeam/event-sink-sse**` (in-BEAM, Elixir) — a production-realistic plugin that registers an `EventSink` and exposes a `GET /events/stream` SSE (Server-Sent Events) endpoint. Incoming `EvilEngine.Types.Event.*` structs are serialized to JSON and pushed to all connected SSE clients. Demonstrates: `facade.register_event_sink.(…)` for event consumption, spinning up a lightweight HTTP listener from within a plugin, managing multiple concurrent SSE connections, and optional severity-based filtering via query params. 1. **Per-app thresholds** — Elixir Mix `test_coverage.threshold` in each child app's `mix.exs`. Prevents regression in apps with functional code. Skeleton/struct-only apps use `threshold: 0`.
