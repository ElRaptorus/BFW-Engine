## 1. Concept-level terms (from `Concept.md` §Glossary)

Some definitions for stack-specific terminologies, in addition to the BPMN
standard:

- **Process Model** or **BPMN** — the BPMN file itself.
- **Definition** or **Process Definition** — the `<bpmn:definitions>` tag of the BPMN file that contains all the Processes.
- **Process** — an executable chain of connected BPMN Flow Elements, starting with a Start Event and ending with an End Event.
- **Process Instance (PI)** — a single execution of a specific Process.
- **Flow Node Instance (FNI)** — a single execution of a specific Flow Node of a specific Process.
- **Event Definition Type** — a nullable qualifier on an FNI that identifies the event definition subtype of the underlying BPMN element (`message`, `signal`, `timer`, `error`, `escalation`, `conditional`, `compensation`, `terminate`, `cancel`, `link`). `null` for non-event flow nodes and plain (untyped) events. `SendTask` and `ReceiveTask` receive `message` (BPMN message-task semantics). Derived from the BPMN model at FNI creation time; stored as `event_type` in the DB and exposed as `eventType` in the SDK.
- **Sub Process Instance** — an instance for an executed Embedded Subprocess, semantically a "Child" of the containing Process Model.
- **Child Process Instance** — an instance of an executed Process which was triggered by a Call Activity. Carries `parent_process_instance_id` and `triggerer_flow_node_instance_id` references back to its parent.
- **Call Activity** — a BPMN activity that invokes another Process by key, spawning a Child Process Instance. Supports FEEL input/output mappings and Error Boundary Events for structured error handling. The parent's Call Activity FNI stores the `child_process_instance_id` in its `type_properties` for bidirectional audit.
- **Exclusive Gateway** — a BPMN gateway that routes a token along exactly one of several paths. Split mode evaluates FEEL conditions on outgoing sequence flows with exactly-one-truthy enforcement (deliberate divergence from BPMN 2.0 "first truthy wins"). Join mode is pure pass-through.
- **Error Boundary Event** — a BPMN boundary event attached to an activity (e.g., Call Activity) that catches errors matching its `errorCode` and/or `errorMessage` using AND logic. Catch-all boundaries (no code, no message) match any error. When matched, the host activity's FNI is interrupted and the error token routes along the boundary's outgoing flows.
- **Execution** — normally starting, running, and finishing a Process Instance. For example: a Process started through an API request.
- **Resuming** — picking up an unfinished Process Instance after an engine (re)start.
- **Retry** — restarting a Process Instance that failed with an error, beginning from a chosen re-entry point in the Flow Node Instance chain. The Process Instance's progress is reset to that point and then picks up from there.
- **Restart** — executing a previously executed Process again, using the exact same settings from a previous execution. Unlike *Retry*, this produces a **completely new** Process Instance.

### DMN terms (Decision Model and Notation)

The DMN API naming parallels the BPMN terms above (BPMN equivalent in parentheses):

- **Decision Definition** — the deployed DMN XML file (`<dmn:definitions>` root container). Analogous to a BPMN Process Definition. Identified by `decision_definition_id` (the DMN definitions `@id` attribute, used as the deploy key). Stored in the `decision_definitions` table; versioned in `decision_versions` (same soft-delete pattern as BPMN).
- **Decision Model** — a single `<dmn:decision>` element inside a Decision Definition. Analogous to a BPMN Process Model. Identified by `decision_model_id` (the `<decision>` element's `@id`). A Decision Definition may contain multiple interconnected Decision Models (DRD), though Phase 2 supports single-decision evaluation only.
- **Decision Version** — an immutable snapshot of a deployed Decision Definition XML. Analogous to a BPMN Process Version. Each deploy of a Decision Definition creates a new Decision Version with a unique `decision_version_id`.
- **Decision Table** — the tabular decision logic inside a `<dmn:decision>` element. Contains inputs, outputs, and rules. Evaluated according to a Hit Policy.
- **Hit Policy** — the rule that governs how matched rules in a Decision Table are reduced to a result. Seven standard policies: UNIQUE, FIRST, ANY, COLLECT, RULE ORDER, OUTPUT ORDER, PRIORITY.
- **Evaluation Trace** — a structured record of every step in a DMN evaluation: which inputs were resolved, which rules matched (and why), which outputs were produced, and timing data. Stored in the BRT FNI's `type_properties.trace` (via `EvaluationTrace.to_json_map/1`) and returned by the `/decisions/{id}/evaluate` endpoint. Supports DRD chaining (multiple `DecisionTrace` entries in dependency order).

> **Naming note:** The DMN spec's full title is "Decision **Model** and Notation", where "Decision Model" informally refers to the whole file. This project departs from that convention: `Decision Definition` = the file, `Decision Model` = an element within it — consistent with how BPMN uses "Process Definition" and "Process Model".

## 2. Implementation-level terms (from `ImplementationPlan.md` Appendix B)

### Identity & contracts

- **Identity** — structured claim `{id, name?, email?, roles?, groups?, claims}` extracted from a verified JWT and attached to every API action for attribution and authorization ([`Authorization.md`](./architecture/authorization.md) §3). `id` ← JWT `sub` (required); `claims` is the full decoded JWT payload map (renamed from the former `raw` field).
- **Data Contract** — a JSON Schema 2020-12 document attached to a BPMN element describing the shape of that element's payload or result.
- **Access Point** — a named command that an external actor (API, plugin, another PI) can invoke on a PI or FNI.
- **PI Facade** — the typed module FNIs use to interact with their containing PI. Sole upward communication channel.

### Events & sinks

- **Event Bus** — the in-process (and future-clustered) pub-sub fabric over which PIs communicate, implemented on top of `Phoenix.PubSub`. This is the *transport* layer; the *sink-routing* layer above it is the `EngineEventBus` (see below).
- **Engine Event Bus (`EngineEventBus`)** (`ImplementationPlan.md` §3.3.2) — the single public fan-out surface for every typed `EvilEngine.Types.Event.*` emitted by `core_execution`. Every `:telemetry.execute/3` call-site inside the engine is paired with exactly one `EvilEngine.Events.EngineEventBus.publish/1`; the bus dispatches the typed event to every registered `@behaviour EvilEngine.Plugin.EventSink` — including the three built-in sinks (`console`, `telemetry`, `websocket`) and any plugin-registered sinks. Dispatch is per-sink parallel, crash-isolated (a crash raises `Event.SinkFailed` back onto the bus and continues other sinks), at-most-once, and non-blocking on the hot path. Built on top of `Phoenix.PubSub`; decouples every producer from every consumer.
- **Event Sink** — a module that implements `@behaviour EvilEngine.Plugin.EventSink` and is registered on boot to receive typed `EvilEngine.Types.Event.*` payloads from `EngineEventBus`. Each sink decides independently which event types it accepts (`accepts?/1`) and how to handle them (`handle_event/2`). Three built-in sinks ship in the engine release: `console` (structured JSON to stdout), `telemetry` (in-process `:telemetry` counters), `websocket` (live Phoenix Channels push). The built-in `database` sink was removed; operators who need DB-backed event storage register a plugin sink. Plugin sinks (Datadog, Kafka, S3 JSONL, custom Postgres replicas, etc.) are registered identically. Sinks are the operator's composition surface for choosing where observability output goes without affecting any other sink's behaviour.

### Retention & housekeeping

- **Retention Policy** (`ImplementationPlan.md` §14.6.2) — a per-terminal-state max-age rule, configured via `EVIL_RETENTION_<STATE>_DAYS` env vars (`FINISHED`, `ERROR`, `FATAL`, `ABORTED`, `ESCALATED`, `COMPENSATED`). The `peripheral_persistence.RetentionRunner` GenServer applies configured policies on an interval (`EVIL_RETENTION_RUN_INTERVAL`, default `PT1H`) in bounded batches (`EVIL_RETENTION_BATCH_SIZE`, default `500`), atomically cascading a delete across `process_instance_events` → `data_object_writes` → `data_objects` → `flow_node_instances` → `process_instances` per eligible PI. Unset policies mean "never purge this state"; the runner only boots if at least one policy is set. A fresh engine installation has zero active policies — retention never kicks in by default.
- **Manual Purge** (`ImplementationPlan.md` §10.2.3 + §14.6.3) — operator-driven cascade delete of terminal PIs older than a supplied cutoff and matching a supplied state list. Surfaced as the admin-only GraphQL mutation `purgeProcessInstances(olderThan, states, dryRun, batchSize)` guarded by the `:can_purge_audit_data` Ash Policy and by the equivalent `evil_engine purge` CLI command. Shares the same atomic-cascade-per-PI semantics as the retention runner (including the "skip PIs with still-running children" rule). `dryRun: true` is the default for both surfaces: the caller sees the row-counts that *would* be deleted without touching the DB. Paired with `Event.RetentionPurged{policy_source: :manual_purge}` so external sinks can distinguish runner-driven from operator-driven purges.

### Plugin layer

- **Plugin Host** — the supervisor + registry responsible for loading, isolating, and routing events to plugins.
- **Seeding Directory** — a filesystem directory whose path is configured via `EVIL_SEEDING_DIRECTORY`. On engine startup the directory is scanned once, and every `.bpmn` file in it is deployed exactly as if it had been `POST`ed to `/processes`. If the env var is unset, no seeding runs.

### Deployment & versioning

- **Latest Version** — for a given process key, the most recently deployed `process_version` row that has `deleted=false` and whose parent `process` row has `enabled=true`. All new PI starts and all Call Activity spawns resolve against this version.
- **Version Deletion** — marking a `process_version` row with `deleted=true`. Executed atomically in one transaction together with `deleted_at=now()` and `deleted_by=<caller identity claim>` (shape: `{id, name?, email?, roles?, groups?, claims}`, same as `started_by` on `process_instances`); a check constraint enforces that `deleted_at`/`deleted_by` are NULL iff `deleted=false`. Blocks any new PI start on that version. Does **not** affect running PIs (they keep executing against their immutable `process_version_id`). Irreversible in v1.
- **Linter Ruleset Score** — an `<evil:linterRulesetScore>` element attached by an external linter to a BPMN's `<evil:properties>` block, summarizing one ruleset evaluation (`rulesetId`, `scorePercent`, `complianceStatus`, `rawErrorFindings`, `rawWarningFindings`, `schemaVersion`, `computedAtIso`, `maxPoints`, `penaltyPoints`). The engine consumes these values at deploy time only; it never produces them.
- **Linter Gate** — the engine-global deploy-time check that compares a BPMN's linter ruleset scores against the thresholds configured in `EVIL_LINTER_GATE`. Runs on both `POST /processes` and (unless `EVIL_LINTER_GATE_SKIP_SEEDING=true`) on Seeding-Directory auto-deploys. A failing BPMN is rejected with `422 Unprocessable Entity` (HTTP) or skipped with an `error` log (seeding). Resume and other operations on already-deployed versions are never gated.

### Contracts & parsed models

- **Published Language** (DDD term) — the set of types a domain exposes to other domains as its stable public contract. In this engine each Core domain publishes types in a single namespace (e.g. `EvilEngine.BPMN.Model.*` for `core_bpmn`; `EvilEngine.Execution.FlowNodeHandler` + `FlowNodeResult` for `core_execution`). Other domains consume the Published Language only — they never reach into private modules. Truly cross-cutting, behavior-free structs (`Identity`, `Token`, event payloads) are promoted into `core_types` so they have a single owner.
- **Parsed Process Model AST** — the typed Elixir-struct representation of a BPMN Process produced by `core_bpmn`'s parser. Root struct is `%EvilEngine.BPMN.Model.Process{}`; Flow Nodes are carried as `%EvilEngine.BPMN.Model.FlowNode{}` with a polymorphic `type_data` field holding one of the per-element `%EvilEngine.BPMN.Model.FlowNodeData.*{}` structs. Every runtime handler consumes this AST by pattern-match — handlers never see raw XML. The AST is the canonical **in-memory** representation of a process definition and is **never persisted**; the authoritative persistent form is `process_versions.bpmn_xml`. A per-node `EvilEngine.BPMN.ModelCache` GenServer (ETS-backed, keyed by `process_version_id`) holds `{AST + compiled Data Contracts + compiled FEEL expressions}` entries. Entries are inserted at deploy time (HTTP + Seeding-Directory) and survive for the engine node's lifetime; on cache miss (cold start, evicted version) `ModelCache.fetch/1` re-parses from `bpmn_xml` (`ImplementationPlan.md` §2.1.3).
- **Model Cache (`EvilEngine.BPMN.ModelCache`)** — per-engine-node GenServer in `core_bpmn`, backed by ETS for concurrent O(1) reads, that owns the runtime mapping `{process_version_id → %EvilEngine.BPMN.Model.Process{}}`. Sole access point for the AST from `core_execution`, handlers, and resume. No serialization, no `model_schema_version`, no forward-compat migrations — the cache is always rebuilt from `bpmn_xml` across engine restarts (`ImplementationPlan.md` §2.1.3).

### Messaging, correlation, and pending-event holds

- **Message Correlation** (`ImplementationPlan.md` §3.5) — the mechanism that routes a named Message Event to the specific PI(s) meant to receive it. Operates on a single `(message_name, correlation_value)` pair. Broadcast-within-key: one published message is delivered to every subscription whose pair matches (serial-letter semantics). Catch-wins-over-Start: if any subscription matches, Message Start Events on the same name are suppressed for that publish.
- **Correlation Key** — the `<evil:correlationKey>` extension on `<bpmn:process>`, a FEEL expression evaluated over PI state or (for Message Start Events) over the inbound payload. Its runtime value is the **expected** correlation value cached on every Message Catch / Boundary / Event-Subprocess-Start subscription this PI registers.
- **Correlation Retrieval Expression** — the `<evil:correlationRetrievalExpression>` extension on a Message Throw / Intermediate Catch / Boundary Event, a FEEL expression evaluated over a message payload (outgoing token for throws, inbound payload for catches). On throws it produces the value stamped onto `messages.correlation_value`; on catches/boundaries it is an optional per-event override of the process-level correlation key. Renamed from `evil:correlationExtraction` for alignment with the BPMN-standard `bpmn:correlationPropertyRetrievalExpression`.
- **Correlation Value** — the resolved string value compared between a subscription's expected value and a published message's stamped value. `:none` (NULL in the DB) is a legitimate value that only matches other `:none` entries — never equal to any concrete string.
- **Pending Message** (`ImplementationPlan.md` §3.5.4) — a row in `pending_messages` representing a published message whose `(name, correlation_value)` had zero matching subscriptions at publish time and which was held for `EVIL_MESSAGE_PENDING_TTL` to allow a late-arriving subscription to still receive it. States: `pending` → `delivered` (matched before TTL) | `expired` (TTL elapsed) | `cancelled` (administrative, not exposed in v1).
- **Signal** — a BPMN broadcast event identified by global `SignalDefinition.name`. No payload, no correlation. One publish delivers to all matching catch/boundary subscriptions and starts all matching Signal Start Events simultaneously (true broadcast). Pending signals use FIFO single-claim drain.
- **Pending Signal** (`ImplementationPlan.md` §3.5.6) — a row in `pending_signals` representing a signal published with zero matching listeners (and zero Signal Start Events fired), held for `EVIL_SIGNAL_PENDING_TTL` to allow a late-registering catch/boundary to still receive it. FIFO single-claim: the first draining subscription transitions the row to `delivered`; subsequent subscribers receive only live broadcasts. Shares the unified `EvilEngine.Events.PendingSweeper` with `pending_messages` and `pending_escalations`.
- **Pending Escalation** (`ImplementationPlan.md` §3.5.7) — a row in `pending_escalations` representing an escalation whose scope-chain walk reached the root of the root PI uncaught. **Observability-only**: the row is inserted *after* the throw-element-aware terminal state has already been applied — the pending row never defers or reverses terminal state. It exists purely so that Escalation Boundary / Event-Subprocess-Start subscriptions registering within `EVIL_ESCALATION_PENDING_TTL` can fire their handler side-effects (non-interrupting token spawn, interrupting cascade on a different PI, audit). Terminal state on the originating PI stays immutable.

### Data Objects

- **Data Object Snapshot** (`ImplementationPlan.md` §4.2) — the current-value row in `data_objects` for a given `(process_instance_id, data_object_id)`. Upserted on every write. Source of truth for runtime reads and for resume-time cache rehydration. Row absence means the Data Object has never been written (is unset). Snapshot rows are **mutable in place**; history lives in `data_object_writes`.
- **Data Object Write** (`ImplementationPlan.md` §4.3) — an immutable row in `data_object_writes` describing one mutation to a Data Object. Captures the causing Flow Node Instance, the written `value`, and a `created_at` timestamp. Every write produces exactly one row; rows are never updated or deleted. Every write is DOA-originated (DOA-only path); the former `source` column (which distinguished `'data_output_association'` from `'handler_api'`) has been removed since there is no handler-API write path in v1. The `data_object_writes` table shares the same column set as `data_objects` (snapshot): `{id, process_instance_id, data_object_id, flow_node_instance_id, value, created_at}`. Together the rows form the full reconstruction trail of "which FNI wrote which value into which Data Object, and when". `previous_value` is not stored in the DB; it is computed from the in-memory cache and carried on the `DataObjectWritten` event only. Historically () a `data_object.written` row was also mirrored in `process_instance_events` by the built-in database sink; that sink is removed and the table is no longer populated.

### Escalations

- **Escalation Scope Chain** (`ImplementationPlan.md` §3.5.7) — the ordered list of enclosing scopes examined by the escalation walker when routing a thrown escalation, starting at the throw-site FNI and walking outward through each Embedded Subprocess / Call Activity / Event Subprocess level in the current PI, then — if the chain reaches the PI's root uncaught and the PI was spawned by a Call Activity — continuing in the parent PI from that Call Activity FNI, and so on recursively. The first matching catch in this order wins; matching stops propagation.
- **Cross-PI Escalation** — an escalation that leaves the PI in which it was thrown because no catch existed anywhere in that PI's scope chain, and is caught by — or passed further up through — the Call Activity FNI in the parent PI. This is the **only** form of cross-PI communication for escalations; escalations never broadcast and never reach unrelated PIs. Both interrupting and non-interrupting Escalation Boundary Events on Call Activities catch cross-PI escalations; the interrupting variant additionally cancels the child PI (and transitive descendants) as part of routing the token out of the boundary.

### Process-Model exposure

- **Process Model Graph (GraphQL)** (`ImplementationPlan.md` §10.2.2) — the GraphQL projection of the parsed `EvilEngine.BPMN.Model.*` AST exposed alongside the Ash persistence resources. Reachable via `ProcessVersion.processModel` and `FlowNodeInstance.flowNode`. Resolvers read `EvilEngine.BPMN.ModelCache` (ETS — no DB, no re-parse). Absinthe types are compile-time-derived from the Elixir struct definitions, so the GraphQL schema cannot drift from the parser. Intended as the **primary structured-Model surface for every external consumer** (Studio debugger, dashboards, CLIs, non-JS operators). Complements the raw-XML `ProcessVersion.bpmnXml` field, which remains authoritative and is still used by `bpmn-js` / `diagram-js` for diagram rendering.
- **Moddle Descriptor** — the `moddle/evil.json` file shipped inside `@evil/engine-client`, declaring the `evil:*` XML namespace to `bpmn-moddle` (the JS BPMN parser underlying `bpmn-js`). Lets any JS/TS consumer that already uses `bpmn-js` parse `evil:*` extensions in raw `bpmnXml` with the exact field shapes and types the engine's own parser produces. **Auto-generated at CI time** by `mix evil.gen.moddle_descriptor` from the `%EvilEngine.BPMN.Model.*{}` struct definitions; a CI diff-guard step fails the build if the generated file is out of sync. Not a replacement for the Process Model Graph — it is a complement for JS views that already need raw XML for diagram rendering (debugger, modeler, live overlays).
- **Engine SDK Parser Re-Export** — the explicit re-export of `EvilEngine.BPMN.Model.*` (AST structs), `EvilEngine.BPMN.ModelCache.fetch/1`, and a read-only facade over <code>EvilEngine.BPMN.Parser.parse_string/1</code> from the `evil_engine_sdk` Hex package. Gives Elixir-side consumers (in-engine plugins, out-of-tree tooling, design-time linters, sidecar sidekicks) direct access to the engine's canonical parser and AST without duplicating parsing logic. The complement of the Moddle Descriptor (JS) and the Process Model Graph (GraphQL, all languages) — three channels, one canonical parser.

### Payload bounds & compression

- **Token Cap** (`ImplementationPlan.md` §5.5 + §10.1.1) — the hard upper bound on canonicalized JSON byte size for every user-supplied payload flowing through the engine — FNI output tokens (`write_result/2`), Data Object values at DOA-commit (DOA-only path), published message/signal/escalation payloads (both via the PI facade and via REST/GraphQL trigger endpoints), PI `started_with_context` at start, User Task completion results, and async Service Task completion/fail payloads via `engine_facade.finish_async_service_task/2` / `fail_async_service_task/3`. Governed by the `EVIL_TOKEN_MAX_BYTES` env var; default `65536` (64 KiB); minimum `1024`; no enforced maximum. Overflow is hard-fail — facade calls return `{:error, :payload_too_large, %{size, limit}}` and transition the causing FNI to `fatal` with a structured reason; REST endpoints return HTTP 413; GraphQL returns a typed error with `extensions.code = "PAYLOAD_TOO_LARGE"`. Measured once at the facade/API boundary before any allocation that scales with payload size. Engine-global: no per-process, per-endpoint, or per-caller override.
- **`gateway_pending_arrivals`** (`ImplementationPlan.md` §4.2) — the dedicated, tightly-scoped table that holds buffered branch arrivals at a parallel or inclusive join gateway until all required branches have fired. Exactly one row per `(gateway_flow_node_instance_id, source_branch_sequence_flow_id)`; uniqueness enforced by index. Rows are inserted as each branch arrives, deleted atomically when the gateway fires (all required branches arrived) or when the enclosing scope is interrupted. Replaces the parallel-join buffering use-case that formerly lived in the deleted `active_tokens` table. Not partitioned — working set bounded by "currently-pending gateway joins across all running PIs" at any instant.
- **`finalTokens`** (`ImplementationPlan.md` §10.2.1.1) — a derived `[Json!]` GraphQL field on `ProcessInstance`, implemented as an Ash calculation that joins `flow_node_instances` WHERE `flow_node_type='endEvent' AND state='finished'` and projects their `output_token` values ordered by `finished_at`. Replaces the eliminated `process_instances.final_token` column. Returns a singleton list for linear `finished` PIs, a list of length N for parallel-End `finished` PIs, and `null` for every non-`finished` terminal state (`fatal`, `aborted`, `error`, `escalated`, `compensated`). Dataloader-batched across list queries so `processInstances { finalTokens }` across 1000 PIs issues two queries total rather than 1001.
- **LZ4 JSONB compression** (`ImplementationPlan.md` §4.2) — Postgres-14+ `COMPRESSION lz4` column modifier applied to every heavy JSONB column in the engine schema (FNI tokens, DO values, write audit, event payloads, gateway arrivals, pending messages/signals/escalations, PI context). Typically delivers 20–40 % storage reduction with a 3–8 % CPU *improvement* over the Postgres default PGLZ on realistic engine workloads, because LZ4 decompression is ~5–10× faster than PGLZ. Configurable via `EVIL_JSONB_COMPRESSION`; Phase 5 load tests gate the default — if LZ4 measures more than 10 % slower than PGLZ on any representative workload, the default reverts to `pglz` before v1.0.0 release.

### Authorization & Identity

- **Identity** (`ImplementationPlan.md` §2.1.1 + [`Authorization.md`](./architecture/authorization.md) §3) — the structured claim extracted from every verified JWT. Fixed mapping: `id` ← JWT `sub` (required — engine refuses tokens without it); `name`, `email` ← optional informational claims; `roles`, `groups` ← optional arrays matched against `<evil:assignees>`; `claims` ← full decoded JWT payload map. Attached to every API action and every PI start request as `%EvilEngine.Types.Identity{}`. Plugin identities carry `id: "plugin:<name>"` with `roles: [:plugin]`.
- **Lane-Claim** ([`Authorization.md`](./architecture/authorization.md) §3.1) — the mapping of BPMN `<bpmn:lane>` elements to JWT claims. Format: `lane:<LANE_NAME> = true`, where `<LANE_NAME>` is the lane's user-facing `name` attribute (not its internal BPMN `id`). The `lane:` prefix prevents collisions with reserved JWT claims (`sub`, `iss`, `aud`, `exp`, etc.). A caller with `lane:Management=true` can interact with flow nodes residing on the "Management" lane.
- **Claim Dictionary** ([`Authorization.md`](./architecture/authorization.md) §4) — the finite set of engine-recognized JWT claims in v1. Boolean claims: `deploy_bpmn`, `delete_bpmn`, `purge_audit_data`, `zeeky_boogie_doog` (admin read-all override), `trigger_message`, `trigger_signal`, `trigger_escalation`, `lane:<name>`. Enum claims: `abort_process_instance` (`none|own|all`), `retry_process_instance` (`none|own|all`), `delete_process_instance` (`none|own|all`). All default to their least-privileged value when absent. Claims outside this set are ignored by the engine but preserved in `Identity.claims` for plugin use.
- **PI Visibility (Option B)** ([`Authorization.md`](./architecture/authorization.md) §5) — the rule governing which Process Instances a caller can see. A PI is visible iff: (a) the caller started it (`started_by.id == caller.sub`), OR (b) any FNI ever on the PI (in any state, including terminal) sits on a lane the caller can access, OR (c) any FNI sits on no lane at all, OR (d) the process has no lanes, OR (e) the caller has `zeeky_boogie_doog=true`. Option B (extended) was chosen over Option A (strict — only active FNIs checked) to preserve audit-trail visibility for terminal PIs: a manager who finished a User Task can still see the PI after it terminates.
- **Privileged Plugin Identity** ([`Authorization.md`](./architecture/authorization.md) §7) — the synthetic `%Identity{id: "plugin:<name>", roles: [:plugin]}` auto-injected by `engine_facade` for all plugin-originated `EvilEngine.Api.*` calls. Bypasses all claim checks — plugins are inside the operator's trust boundary. Audit is preserved: every invocation records the plugin identity.
- **Execution-Time Authorization Detachment** ([`Authorization.md`](./architecture/authorization.md) §8) — the invariant that once a PI starts, the starting user's JWT claims are never re-checked. Call Activities, Resume, timer-triggered transitions, and async dispatch all run without ongoing JWT validation. JWT expiry mid-execution has zero effect on the running PI.

### Engine-level audit retention

- **Engine-Level Audit Tables** (`ImplementationPlan.md` §4.3 + §14.6) — the tables that record engine-wide publish/raise/fire events orthogonal to any single PI — `messages`, `pending_messages`, `signals`, `pending_signals`, `escalations`, `pending_escalations`, `compensations`, and the terminal-state (`fired`/`cancelled`) rows of `engine_timers`. Distinguished from PI-scoped audit tables (`process_instance_events`, `data_object_writes`) by having no foreign key into `process_instances`: the relation to PIs is via JSONB content (`messages.correlations[]`, `origin`) or is inherently absent (API-published messages with zero matches, broadcast signals with no listeners). Consequently they fall outside PI-cascade retention and need their own cleanup story (see `Engine-Audit Retention`). All partitioned monthly on their respective publish/trigger timestamp from v1 — except `engine_timers`, which is not partitioned (rationale in `ImplementationPlan.md` §4.3).
- **Engine-Audit Retention** (`ImplementationPlan.md` §14.6.2) — the opt-in second pass of the `RetentionRunner` that sweeps Engine-Level Audit Tables. Governed by a single env var `EVIL_RETENTION_ENGINE_AUDIT_DAYS` (unset by default — a fresh install never auto-purges these rows). One cutoff applies to all tables; per-table batched DELETE, partition-aware so each batch prunes one or two old partitions. Excludes operational-state rows (`pending_messages.state='pending'`, `pending_signals.state='pending'`, `pending_escalations.state='pending'`, `engine_timers.state='armed'`) — those are live execution state, never retention-eligible. Emits one `Event.EngineAuditPurged{table, cutoff, row_count, policy_source: :retention_runner}` per table per tick onto `EngineEventBus`. Independent of PI retention — operators can enable engine-audit retention without any PI-scoped policy, and vice versa.
- **Delete-on-Transition (pending tables)** (`ImplementationPlan.md` §3.5.4 + §3.5.6 + §3.5.7) — the behavior toggles `EVIL_PENDING_MESSAGES_KEEP_AFTER_TRANSITION`, `EVIL_PENDING_SIGNALS_KEEP_AFTER_TRANSITION`, and `EVIL_PENDING_ESCALATIONS_KEEP_AFTER_TRANSITION`; each defaults to `true`. With the default, a pending row persists in its table after its state transitions to `delivered`/`expired`/`cancelled`, becoming a delivery-attempt audit record that engine-audit retention later ages out. With the flag set to `false`, the engine physically deletes the row in the same transaction that moves its state away from `pending`, so the table holds only live (in-flight) rows. Never affects rows still in `pending` state — those always persist until their state transitions or the TTL sweeper expires them. Provides a zero-retention path for operators who don't need delivery-attempt audit, independent of the general engine-audit retention knob.
- **`Event.EngineAuditPurged`** (`ImplementationPlan.md` §2) — the typed event struct emitted once per engine-audit table per retention tick when that pass deletes any rows. Payload: `%{table :: atom, cutoff :: DateTime.t(), row_count :: non_neg_integer(), policy_source :: :retention_runner}`. Distinct from `Event.RetentionPurged` (PI-scoped) because the granularity and the "what was deleted" shape are different — a PI-scoped purge deletes exactly one PI's worth of rows across five related tables atomically, while an engine-audit purge is a batched sweep over one table at a time with no PI affinity.
