# Glossary

This is the engine's glossary: BPMN vocabulary the product uses, plus
implementation terms (schema, events, identity, retention). Link here
instead of redefining a term.

---

## 1. Concept-level terms (from the original product concept)

Some definitions for stack-specific terminologies, in addition to the BPMN
standard:

- **Process Model** or **BPMN** — the BPMN file itself.
- **Definition** or **Process Definition** — the `<bpmn:definitions>` tag of the BPMN file that contains all the Processes.
- **Process** — an executable chain of connected BPMN Flow Elements, starting with a Start Event and ending with an End Event.
- **Process Instance (PI)** — a single execution of a specific Process.
- **Flow Node Instance (FNI)** — a single execution of a specific Flow Node of a specific Process.
- **Event Definition Type** — a nullable qualifier on an FNI that identifies the event definition subtype of the underlying BPMN element (`message`, `signal`, `timer`, `error`, `escalation`, `conditional`, `compensation`, `terminate`, `cancel`, `link`). `null` for non-event flow nodes and plain (untyped) events. `SendTask` and `ReceiveTask` receive `message` (BPMN message-task semantics). Derived from the BPMN model at FNI creation time; stored as `event_type` in the DB and exposed as `eventType` in the SDK.
- **Sub Process Instance** — an instance for an executed Embedded Subprocess, semantically a "Child" of the containing Process Model.
- **Child Process Instance** — an instance of an executed Process which was triggered by a Call Activity. Carries `parent_process_instance_id` and `triggerer_flow_node_instance_id` references back to its parent.
- **Call Activity** — a BPMN activity that invokes another Process by key, spawning a Child Process Instance. Supports FEEL input/output mappings and Error Boundary Events for structured error handling. The parent's Call Activity FNI stores the `child_process_instance_id` in its `type_properties` for bidirectional audit.
- **Exclusive Gateway** — a BPMN gateway that routes a token along exactly one of several paths. Split mode evaluates FEEL conditions on outgoing sequence flows with exactly-one-truthy enforcement (deliberate divergence from BPMN 2.0 "first truthy wins"). Join mode is pure pass-through.
- **Error Boundary Event** — a BPMN boundary event attached to an activity (e.g., Call Activity) that catches errors matching its `errorCode` and/or `errorMessage` using AND logic. Catch-all boundaries (no code, no message) match any error. When matched, the host activity's FNI is interrupted and the error token routes along the boundary's outgoing flows.
- **Execution** — normally starting, running, and finishing a Process Instance. For example: a Process started through an API request.
- **Resuming** — picking up an unfinished Process Instance after an engine (re)start.
- **Retry** — restarting a Process Instance that failed with an error, beginning from a chosen re-entry point in the Flow Node Instance chain. The Process Instance's progress is reset to that point and then picks up from there.
- **Restart** — executing a previously executed Process again, using the exact same settings from a previous execution. Unlike *Retry*, this produces a **completely new** Process Instance.

### DMN terms (Decision Model and Notation)

The DMN API naming parallels the BPMN terms above (BPMN equivalent in parentheses):

- **Decision Definition** — the deployed DMN XML file (`<dmn:definitions>` root container). Analogous to a BPMN Process Definition. Identified by `decision_definition_id` (the DMN definitions `@id` attribute, used as the deploy key). Stored in the `decision_definitions` table; versioned in `decision_versions` (same soft-delete pattern as BPMN).
- **Decision Model** — a single `<dmn:decision>` element inside a Decision Definition. Analogous to a BPMN Process Model. Identified by `decision_model_id` (the `<decision>` element's `@id`). A Decision Definition may contain multiple interconnected Decision Models (DRD), though Phase 2 supports single-decision evaluation only.
- **Decision Version** — an immutable snapshot of a deployed Decision Definition XML. Analogous to a BPMN Process Version. Each deploy of a Decision Definition creates a new Decision Version with a unique `decision_version_id`.
- **Decision Table** — the tabular decision logic inside a `<dmn:decision>` element. Contains inputs, outputs, and rules. Evaluated according to a Hit Policy.
- **Hit Policy** — the rule that governs how matched rules in a Decision Table are reduced to a result. Seven standard policies: UNIQUE, FIRST, ANY, COLLECT, RULE ORDER, OUTPUT ORDER, PRIORITY.
- **Evaluation Trace** — a structured record of every step in a DMN evaluation: which inputs were resolved, which rules matched (and why), which outputs were produced, and timing data. Stored in the BRT FNI's `type_properties.trace` (via `EvaluationTrace.to_json_map/1`) and returned by the `/decisions/{id}/evaluate` endpoint. Supports DRD chaining (multiple `DecisionTrace` entries in dependency order).

> **Naming note:** The DMN spec's full title is "Decision **Model** and Notation", where "Decision Model" informally refers to the whole file. This project departs from that convention: `Decision Definition` = the file, `Decision Model` = an element within it — consistent with how BPMN uses "Process Definition" and "Process Model".

## Implementation-level terms

### Identity & contracts

- **Identity** — structured claim `{id, name?, email?, roles?, groups?, claims}` extracted from a verified JWT and attached to every API action for attribution and authorization ([`Authorization.md`](./architecture/authorization.md) §3). `id` ← JWT `sub` (required); `claims` is the full decoded JWT payload map (renamed from the former `raw` field).
- **Data Contract** — a JSON Schema 2020-12 document attached to a BPMN element describing the shape of that element's payload or result.
- **Access Point** — a named command that an external actor (API, plugin, another PI) can invoke on a PI or FNI.
- **PI Facade** — the typed module FNIs use to interact with their containing PI. Sole upward communication channel.

### Events & sinks

- **Event Bus** — the in-process (and future-clustered) pub-sub fabric over which PIs communicate, implemented on top of `Phoenix.PubSub`. This is the *transport* layer; the *sink-routing* layer above it is the `EngineEventBus` (see below).
- **Engine Event Bus (`EngineEventBus`)** — the single public fan-out surface for every typed `EvilEngine.Types.Event.*` emitted by `core_execution`. Every `:telemetry.execute/3` call-site inside the engine is paired with exactly one `EvilEngine.Events.EngineEventBus.publish/1`; the bus dispatches the typed event to every registered `@behaviour EvilEngine.Plugin.EventSink` — including the three built-in sinks (`console`, `telemetry`, `websocket`) and any plugin-registered sinks. Dispatch is per-sink parallel, crash-isolated (a crash raises `Event.SinkFailed` back onto the bus and continues other sinks), at-most-once, and non-blocking on the hot path. Built on top of `Phoenix.PubSub`; decouples every producer from every consumer.
- **Event Sink** — a module that implements `@behaviour EvilEngine.Plugin.EventSink` and is registered on boot to receive typed `EvilEngine.Types.Event.*` payloads from `EngineEventBus`. Each sink decides independently which event types it accepts (`accepts?/1`) and how to handle them (`handle_event/2`). Three built-in sinks ship in the engine release: `console` (structured JSON to stdout), `telemetry` (in-process `:telemetry` counters), `websocket` (live Phoenix Channels push). The built-in `database` sink was removed; operators who need DB-backed event storage register a plugin sink. Plugin sinks (Datadog, Kafka, S3 JSONL, custom Postgres replicas, etc.) are registered identically. Sinks are the operator's composition surface for choosing where observability output goes without affecting any other sink's behaviour.

### Retention & housekeeping

- **Retention Policy** — a per-terminal-state max-age rule, configured via `TDE_RETENTION_<STATE>_DAYS` env vars (`FINISHED`, `ERROR`, `FATAL`, `ABORTED`, `ESCALATED`, `COMPENSATED`, `CANCELLED`). `mix evil.retention.purge` applies configured policies in bounded batches (`TDE_RETENTION_BATCH_SIZE`, default `500`), hard-deleting a root tree (skip if any descendant is `running` or `suspended`). Unset policies mean "never purge this state". Cron/systemd owns the interval (`TDE_RETENTION_RUN_INTERVAL` is ignored). A fresh engine installation has zero active policies — retention never kicks in by default. There is no RetentionRunner GenServer.
- **Manual Purge** ([api.md](./architecture/api.md) §10.2.3 + [configuration.md](./architecture/configuration.md) §14.6.3) — REST/CLI `purge` is **deferred / not v1**. Operators schedule the Mix task or run SQL. `purge_audit_data` is unused. GraphQL has no purge mutation.

### Plugin layer

- **Plugin Host** — the supervisor + registry responsible for loading, isolating, and routing events to plugins.
- **Seeding Directory** — a filesystem directory whose path is configured via `TDE_SEEDING_DIRECTORY`. On engine startup the directory is scanned once, and every `.bpmn` file in it is deployed exactly as if it had been `POST`ed to `/processes`. If the env var is unset, no seeding runs.

### Deployment & versioning

- **Latest Version** — for a given process key, the most recently deployed `process_version` row that has `deleted=false` and whose parent `process` row has `enabled=true`. All new PI starts and all Call Activity spawns resolve against this version.
- **Version Deletion** — marking a `process_version` row with `deleted=true`. Executed atomically in one transaction together with `deleted_at=now()` and `deleted_by=<caller identity claim>` (shape: `{id, name?, email?, roles?, groups?, claims}`, same as `started_by` on `process_instances`); a check constraint enforces that `deleted_at`/`deleted_by` are NULL iff `deleted=false`. Blocks any new PI start on that version. Does **not** affect running PIs (they keep executing against their immutable `process_version_id`). Irreversible in v1.
- **Linter Ruleset Score** — an `<evil:linterRulesetScore>` element attached by an external linter to a BPMN's `<evil:properties>` block, summarizing one ruleset evaluation (`rulesetId`, `scorePercent`, `complianceStatus`, `rawErrorFindings`, `rawWarningFindings`, `schemaVersion`, `computedAtIso`, `maxPoints`, `penaltyPoints`). The engine consumes these values at deploy time only; it never produces them.
- **Linter Gate** — the engine-global deploy-time check that compares a BPMN's linter ruleset scores against the thresholds configured in `TDE_LINTER_GATE`. Runs on both `POST /processes` and (unless `TDE_LINTER_GATE_SKIP_SEEDING=true`) on Seeding-Directory auto-deploys. A failing BPMN is rejected with `422 Unprocessable Entity` (HTTP) or skipped with an `error` log (seeding). Resume and other operations on already-deployed versions are never gated.

### Contracts & parsed models

- **Published Language** (DDD term) — the set of types a domain exposes to other domains as its stable public contract. In this engine each Core domain publishes types in a single namespace (e.g. `EvilEngine.BPMN.Model.*` for `core_bpmn`; `EvilEngine.Execution.FlowNodeHandler` + `FlowNodeResult` for `core_execution`). Other domains consume the Published Language only — they never reach into private modules. Truly cross-cutting, behavior-free structs (`Identity`, `Token`, event payloads) are promoted into `core_types` so they have a single owner.
- **Parsed Process Model AST** — the typed Elixir-struct representation of a BPMN Process produced by `core_bpmn`'s parser. Root struct is `%EvilEngine.BPMN.Model.Process{}`; Flow Nodes are carried as `%EvilEngine.BPMN.Model.FlowNode{}` with a polymorphic `type_data` field holding one of the per-element `%EvilEngine.BPMN.Model.FlowNodeData.*{}` structs. Every runtime handler consumes this AST by pattern-match — handlers never see raw XML. The AST is the canonical **in-memory** representation of a process definition and is **never persisted**; the authoritative persistent form is `process_versions.bpmn_xml`. A per-node `EvilEngine.BPMN.ModelCache` GenServer (ETS-backed, keyed by `process_version_id`) holds `{AST + compiled Data Contracts + compiled FEEL expressions}` entries. Entries are inserted at deploy time (HTTP + Seeding-Directory) and survive for the engine node's lifetime; on cache miss (cold start, evicted version) `ModelCache.fetch/1` re-parses from `bpmn_xml`.
- **Model Cache (`EvilEngine.BPMN.ModelCache`)** — per-engine-node GenServer in `core_bpmn`, backed by ETS for concurrent O(1) reads, that owns the runtime mapping `{process_version_id → %EvilEngine.BPMN.Model.Process{}}`. Sole access point for the AST from `core_execution`, handlers, and resume. No serialization, no `model_schema_version`, no forward-compat migrations — the cache is always rebuilt from `bpmn_xml` across engine restarts.

### Messaging, correlation, and pending-event holds

- **Message Correlation** — the mechanism that routes a named Message Event to the specific PI(s) meant to receive it. Operates on a single `(message_name, correlation_value)` pair. Broadcast-within-key: one published message is delivered to every subscription whose pair matches (serial-letter semantics). Catch-wins-over-Start: if any subscription matches, Message Start Events on the same name are suppressed for that publish.
- **Correlation Key** — the `<evil:correlationKey>` extension on `<bpmn:process>`, a FEEL expression evaluated over PI state or (for Message Start Events) over the inbound payload. Its runtime value is the **expected** correlation value cached on every Message Catch / Boundary / Event-Subprocess-Start subscription this PI registers.
- **Correlation Retrieval Expression** — the `<evil:correlationRetrievalExpression>` extension on a Message Throw / Intermediate Catch / Boundary Event, a FEEL expression evaluated over a message payload (outgoing token for throws, inbound payload for catches). On throws it produces the value stamped onto `messages.correlation_value`; on catches/boundaries it is an optional per-event override of the process-level correlation key. Renamed from `evil:correlationExtraction` for alignment with the BPMN-standard `bpmn:correlationPropertyRetrievalExpression`.
- **Correlation Value** — the resolved string value compared between a subscription's expected value and a published message's stamped value. `:none` (NULL in the DB) is a legitimate value that only matches other `:none` entries — never equal to any concrete string.
- **Pending Message** — a row in `pending_messages` representing a published message whose `(name, correlation_value)` had zero matching subscriptions at publish time and which was held for `TDE_MESSAGE_PENDING_TTL` to allow a late-arriving subscription to still receive it. States: `pending` → `delivered` (matched before TTL) | `expired` (TTL elapsed) | `cancelled` (administrative, not exposed in v1).
- **Signal** — a BPMN broadcast event identified by global `SignalDefinition.name`. No payload, no correlation. One publish delivers to all matching catch/boundary subscriptions and starts all matching Signal Start Events simultaneously (true broadcast). Pending signals use FIFO single-claim drain.
- **Pending Signal** — a row in `pending_signals` representing a signal published with zero matching listeners (and zero Signal Start Events fired), held for `TDE_SIGNAL_PENDING_TTL` to allow a late-registering catch/boundary to still receive it. FIFO single-claim: the first draining subscription transitions the row to `delivered`; subsequent subscribers receive only live broadcasts. Shares the unified `EvilEngine.Events.PendingSweeper` with `pending_messages`. There is no `pending_escalations` table.
- **Pending Escalation** — **dropped.** There is no `pending_escalations` table, no late-catch drain, and no `PendingSweeper` involvement for escalations. Boundaries are pre-spawned in `:waiting` when the host activity starts; propagation is deterministic parent-chain message passing. See [routing.md](./architecture/routing.md) §3.5.7.

### Data Objects

- **Data Object Snapshot** — the current-value row in `data_objects` for a given `(process_instance_id, data_object_id)`. Upserted on every write. Source of truth for runtime reads and for resume-time cache rehydration. Row absence means the Data Object has never been written (is unset). Snapshot rows are **mutable in place**; history lives in `data_object_writes`.
- **Data Object Write** — an immutable row in `data_object_writes` describing one mutation to a Data Object. Captures the causing Flow Node Instance, the written `value`, and a `created_at` timestamp. Every write produces exactly one row; rows are never updated or deleted. Every write is DOA-originated (DOA-only path); the former `source` column (which distinguished `'data_output_association'` from `'handler_api'`) has been removed since there is no handler-API write path in v1. The `data_object_writes` table shares the same column set as `data_objects` (snapshot): `{id, process_instance_id, data_object_id, flow_node_instance_id, value, created_at}`. Together the rows form the full reconstruction trail of "which FNI wrote which value into which Data Object, and when". `previous_value` is not stored in the DB; it is computed from the in-memory cache and carried on the `DataObjectWritten` event only. Historically a `data_object.written` row was also mirrored in `process_instance_events` by the built-in database sink; that sink is removed and the table is no longer populated.

### Escalations

- **Escalation Scope Chain** §3.5.7) — the ordered sequence of enclosing scopes an escalation traverses outward from its throw site. There is **no centralized walker**: propagation is deterministic and synchronous via per-scope message passing — each handler Task / PI independently handles the escalation message it receives, one scope at a time, and passes it further out only on no-match. At each scope the candidate order is **proximity-first**: a boundary event on the activity being exited, then the scope's **Event Subprocess escalation start** (resolved reactively via `EventSubprocessResolver.find_matching_escalation_start/2`, specific code beats catch-all among peer ESP starts), then — if uncaught — the next enclosing scope; a Call Activity boundary in the parent PI is reached only after the child PI's own chain is exhausted. The first match in this order wins and stops propagation.
- **Cross-PI Escalation** — an escalation that leaves the PI in which it was thrown because no catch existed anywhere in that PI's scope chain, and is caught by — or passed further up through — the Call Activity FNI in the parent PI. This is the **only** form of cross-PI communication for escalations; escalations never broadcast and never reach unrelated PIs. Both interrupting and non-interrupting Escalation Boundary Events on Call Activities catch cross-PI escalations; the interrupting variant additionally cancels the child PI (and transitive descendants) as part of routing the token out of the boundary.

### Subprocesses & Event Subprocesses

- **Event Subprocess (ESP)** §Event Subprocess Handler) — a `<bpmn:subProcess triggeredByEvent="true">` placed inside a process or embedded subprocess. It has **no incoming or outgoing sequence flows** and is never token-entered. It lies **dormant** until its single **typed** start event (Message, Signal, Timer, Error, Escalation, or Conditional) is triggered by an event occurring within its enclosing scope; on trigger the scope PI spawns a **child PI** running the ESP's inner flow (same child-PI model as an embedded subprocess — synthetic model, same `process_version_id`, no separate deployment). Handled by `EvilEngine.Execution.FlowNodes.EventSubprocess`. Distinct from an **Embedded Subprocess** (`triggeredByEvent="false"`), which *is* entered by a token arriving on an incoming sequence flow.
- **ESP Scope** — the enclosing process or embedded-subprocess PI that **owns** an Event Subprocess's trigger. The scope PI delegates to the scope-level trigger API in `FlowNodes.EventSubprocess` (aliased as `EspScope` in the PI): `register_triggers/1` registers dormant triggers on init/resume, `resolve_trigger/3` / `resolve_error_catch/3` / `resolve_bpmn_error_catch/2` / `resolve_escalation_catch/2` / `evaluate_conditionals/1` detect triggering events and return `trigger_action()` tuples (`{:fire_interrupting, ...}`, `{:fire_non_interrupting, ...}`, or `:noop`), which the PI executes through thin delegation (`execute_esp_action/2`). An ESP catches error/escalation raised **within its scope** before propagation to the parent (proximity). An interrupting fire cancels the scope's *other* active/waiting FNIs (`interrupt_remaining_fnis`, reason `:interrupted_by_event_subprocess`) but does **not** kill the scope PI — the scope reaches `:finished` once the ESP child completes.
- **Interrupting Start Event** (`isInterrupting="true"`, the BPMN default) — an Event Subprocess start event that, on trigger, cancels every other active/waiting FNI in the ESP scope and then runs the ESP child; the scope finishes when the ESP child completes. An Error ESP start **must** be interrupting (ESP-D7). Modeler-controlled only (no `evil:*` override, no property-pane toggle).
- **Non-Interrupting Start Event** (`isInterrupting="false"`) — an Event Subprocess start event that spawns an ESP child PI running **in parallel** with the rest of the scope. It may fire multiple times — each fire spawns an independent child PI — and the scope finishes only once the main flow **and** every ESP child PI have completed. Valid for Message/Signal/Timer/Conditional/Escalation starts; **not** for Error (which must interrupt).

### Process-Model exposure

- **Process Model Graph (GraphQL)** (`api.md` §10.2.2) — the GraphQL projection of the parsed `EvilEngine.BPMN.Model.*` AST exposed alongside the Ash persistence resources. Reachable via `ProcessVersion.processModel` and `FlowNodeInstance.flowNode` / `FlowNodeInstance.processVersion`. Resolvers read `EvilEngine.BPMN.ModelCache` (ETS on a warm hit; a DB read + re-parse on a cold miss — see `architecture/common-pitfalls.md`, Warm `ModelCache` only after the deploy transaction commits). Absinthe types are declared against a per-struct field table (`EvilEngineWeb.Graphql.ModelSchema.FieldTable`) with a compile-time completeness check that fails the build if any struct field is neither mapped nor explicitly excluded — a new struct field cannot silently leak or silently vanish. Intended as the **primary structured-Model surface for every external consumer** (Studio debugger, dashboards, CLIs, non-JS operators). Complements the raw-XML `ProcessVersion.bpmnXml` field, which remains authoritative and is still used by `bpmn-js` / `diagram-js` for diagram rendering.
- **Extension Manifest** (`extension-manifest.json`) — the declarative registry of every `evil:*` BPMN extension element the parser reads, generated by `mix evil.gen.extension_manifest` (`apps/core_bpmn/lib/mix/tasks/evil.gen.extension_manifest.ex`) from `EvilEngine.BPMN.ExtensionManifest`. One entry per element: `element`, `valueKind` (`feel` | `json_schema` | `static_string` | `integer` | `boolean` | `mapping`), `carrier` (`body` | `attributes`), `attributes`, `applicableTo` (BPMN element types it's read on), and `modelField` (the Elixir struct field it populates), plus a top-level `extensible` list naming generic containers the Engine does not interpret (`Properties`/`Property`). Shipped as a typed export in `@elraptorus/daemonengine_sdk` (`packages/js/sdk/src/generated/extension-manifest.ts`). **Supersedes the Moddle Descriptor plan** (decision D-5 = B+, see `.cursor/plans/process_model_graphql_exposure_205a61a4.plan.md`): the Engine's parser has no `allowedIn`/type-hierarchy concept, so it cannot honestly generate a full moddle descriptor — only the extension *vocabulary* it actually reads. The Studio keeps its hand-written `evil-platform.json` moddle descriptor and runs a bidirectional conformance test against this manifest instead of consuming a generated descriptor.
- **Engine SDK Parser Re-Export** — the explicit re-export of `EvilEngine.BPMN.Model.*` (AST structs), `EvilEngine.BPMN.ModelCache.{fetch/1, get/1, fetch_subprocess_model/2, find_message_start_events/1, find_signal_start_events/1}`, and `EvilEngine.BPMN.Parser.parse/1`, via `EvilEngine.SDK.BPMN` (`apps/engine_sdk/lib/evil_engine/sdk/bpmn.ex`) in the `evil_engine_sdk` app. Gives Elixir-side consumers (in-engine plugins, out-of-tree tooling, design-time linters, sidecar sidekicks) direct access to the engine's canonical parser and AST without duplicating parsing logic. The complement of the Extension Manifest (JS vocabulary) and the Process Model Graph (GraphQL, all languages) — three channels, one canonical parser.

### Payload bounds & compression

- **Token Cap** — the hard upper bound on canonicalized JSON byte size for every user-supplied payload flowing through the engine — FNI output tokens (`write_result/2`), Data Object values at DOA-commit (DOA-only path), published message/signal/escalation payloads (both via the PI facade and via REST trigger endpoints), PI `started_with_context` at start, User Task completion results, and async Service Task completion/fail payloads via `engine_facade.finish_async_service_task/2` / `fail_async_service_task/3`. Governed by the `TDE_TOKEN_MAX_BYTES` env var; default `65536` (64 KiB); minimum `1024`; no enforced maximum. Overflow is hard-fail — facade calls return `{:error, :payload_too_large, %{size, limit}}` and transition the causing FNI to `fatal` with a structured reason; REST endpoints return HTTP 413. Measured once at the facade/API boundary before any allocation that scales with payload size. Engine-global: no per-process, per-endpoint, or per-caller override.
- **`gateway_pending_arrivals`** — the dedicated, tightly-scoped table that holds buffered branch arrivals at a parallel or inclusive join gateway until all required branches have fired. Exactly one row per `(gateway_flow_node_instance_id, source_branch_sequence_flow_id)`; uniqueness enforced by index. Rows are inserted as each branch arrives, deleted atomically when the gateway fires (all required branches arrived) or when the enclosing scope is interrupted. Replaces the parallel-join buffering use-case that formerly lived in the deleted `active_tokens` table. Not partitioned — working set bounded by "currently-pending gateway joins across all running PIs" at any instant.
- **`finalTokens`** — a derived `[Json!]` GraphQL field on `ProcessInstance`, implemented as an Ash calculation that joins `flow_node_instances` WHERE `flow_node_type='endEvent' AND state='finished'` and projects their `output_token` values ordered by `finished_at`. Replaces the eliminated `process_instances.final_token` column. Returns a singleton list for linear `finished` PIs, a list of length N for parallel-End `finished` PIs, and `null` for every non-`finished` terminal state (`fatal`, `aborted`, `error`, `escalated`, `compensated`). Dataloader-batched across list queries so `processInstances { finalTokens }` across 1000 PIs issues two queries total rather than 1001.
- **LZ4 JSONB compression** — Postgres-14+ `COMPRESSION lz4` column modifier applied to every heavy JSONB column in the engine schema (FNI tokens, DO values, write audit, event payloads, gateway arrivals, pending messages/signals, PI context). Configurable via `TDE_JSONB_COMPRESSION`. Measured comparison vs PGLZ: [database.md](guides/operations/database.md).

### Authorization & Identity

- **Identity** §3) — the structured claim extracted from every verified JWT. Fixed mapping: `id` ← JWT `sub` (required — engine refuses tokens without it); `name`, `email` ← optional informational claims; `roles`, `groups` ← optional arrays matched against `<evil:assignees>`; `claims` ← full decoded JWT payload map. Attached to every API action and every PI start request as `%EvilEngine.Types.Identity{}`. Plugin identities carry `id: "plugin:<name>"` with `roles: [:plugin]`.
- **Lane-Claim** ([`Authorization.md`](./architecture/authorization.md) §3.1) — the mapping of BPMN `<bpmn:lane>` elements to JWT claims. Format: `lane:<LANE_NAME> = "read" | "write"`, where `<LANE_NAME>` is the lane's user-facing `name` attribute (not its internal BPMN `id`). Boolean `true` is rejected. The `lane:` prefix prevents collisions with reserved JWT claims (`sub`, `iss`, `aud`, `exp`, etc.). `"write"` acts; `"read"` observes.
- **Claim Dictionary** ([`Authorization.md`](./architecture/authorization.md) §4) — the finite set of engine-recognized JWT claims in v1. Boolean claims: `deploy_bpmn`, `delete_bpmn`, `purge_audit_data`, `zeeky_boogie_doog` (admin read+write override), `observe_all` (unbounded read, never write), `trigger_message`, `trigger_signal`, `trigger_escalation`. Lane claims: `lane:<name>` (`"read"` \| `"write"`; boolean `true` is rejected). Enum claims: `abort_process_instance` (`none|own|all`), `retry_process_instance` (`none|own|all`), `delete_process_instance` (`none|own|all`). All default to their least-privileged value when absent. Claims outside this set are ignored by the engine but preserved in `Identity.claims` for plugin use.
- **PI Visibility (Option B)** ([`Authorization.md`](./architecture/authorization.md) §5) — the rule governing which Process Instances a caller can see. A PI is visible iff: (a) the caller started it (`started_by.id == caller.sub`), OR (b) any FNI ever on the PI (in any state, including terminal) sits on a lane the caller can access (`"read"` or `"write"`), OR (c) any FNI sits on no lane at all, OR (d) the process has no lanes, OR (e) the caller has `zeeky_boogie_doog=true`, OR (f) the caller has `observe_all=true`. Option B (extended) was chosen over Option A (strict — only active FNIs checked) to preserve audit-trail visibility for terminal PIs: a manager who finished a User Task can still see the PI after it terminates.
- **Privileged Plugin Identity** ([`Authorization.md`](./architecture/authorization.md) §7) — the synthetic `%Identity{id: "plugin:<name>", roles: [:plugin]}` auto-injected by `engine_facade` for all plugin-originated `EvilEngine.Api.*` calls. Bypasses all claim checks — plugins are inside the operator's trust boundary. Audit is preserved: every invocation records the plugin identity.
- **Execution-Time Authorization Detachment** ([`Authorization.md`](./architecture/authorization.md) §8) — the invariant that once a PI starts, the starting user's JWT claims are never re-checked. Call Activities, Resume, timer-triggered transitions, and async dispatch all run without ongoing JWT validation. JWT expiry mid-execution has zero effect on the running PI.

### Engine-level audit retention

- **Engine-Level Audit Tables** — the tables that record engine-wide publish events orthogonal to any single PI. **Shipped today:** `messages`, `pending_messages`, `signals`, `pending_signals`. There is no `pending_escalations` table. There are no `escalations`, `compensations`, or `engine_timers` tables. `timer_start_schedules` is operational (not engine-audit) and must not be deleted by audit SQL. Distinguished from PI-scoped audit tables (`process_instance_events`, `data_object_writes`) by having no foreign key into `process_instances`. Consequently they fall outside PI-cascade retention and need their own cleanup (see `Engine-Audit Retention`). The shipped four are partitioned on `published_at`.
- **Engine-Audit Retention** — operator SQL that sweeps Engine-Level Audit Tables (`messages`, `pending_messages`, `signals`, `pending_signals`). Governed by the unused engine convention `TDE_RETENTION_ENGINE_AUDIT_DAYS` (unset by default). Recipe in [database.md](guides/operations/database.md). Excludes operational-state rows (`pending_messages.state='pending'`, `pending_signals.state='pending'`). Independent of Mix `evil.retention.purge`. There is no in-engine sweeper and no `Event.EngineAuditPurged`.
- **Delete-on-Transition (pending tables)** — toggles `TDE_PENDING_MESSAGES_KEEP_AFTER_TRANSITION` and `TDE_PENDING_SIGNALS_KEEP_AFTER_TRANSITION`; each defaults to `true`. With the default, a pending row persists after its state transitions to `delivered`/`expired`/`cancelled`, becoming a delivery-attempt audit record that operator SQL later ages out. With the flag set to `false`, the engine physically deletes the row on deliver/expire/cancel (`destroy_if_pending` still requires `state == 'pending'`), so the table holds only live (in-flight) rows. There is no pending-escalation table.
- **`Event.EngineAuditPurged` / `Event.RetentionPurged`** — **not shipped**. Purge observability is Mix/cron logs and operator SQL.
